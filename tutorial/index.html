Try the Grab Lab ↗Download this guide ↓

Read the explanation, then test the feel.

Build a small Unity VR playground, pick up a real Rigidbody, and switch its controller while the object is still in your hand. Compare a native ConfigurableJoint, relative-velocity PD, and backward PD. Press the same cube against the same wall, rotate it, release it, and decide which feels better in a headset.

That is the useful experiment behind FireBlast’s setup: responsive hand locomotion and physical grabbed objects can coexist. A graph helps explain a problem; the in-headset A/B decides whether the solution feels good.

Start here: Unity starter kit · WebXR companion · Physics Gym comparison · Source repository

This is a teaching implementation for Unity 6 with OpenXR, including the Unity 6.3 workflow. The C# kit has not been executed in Unity or tested on a headset during its creation. Run the checks below before treating it as a foundation for a shipped game. The browser companion is an independently implemented experiment, not a Unity or PhysX emulator.

1. From an empty project to the teaching scene#

Install the project dependencies#

  1. Create a Unity 6 3D Built-In or Universal 3D project. Use a blank scene. Install Android Build Support, including its SDK/NDK and OpenJDK modules, through Unity Hub if you intend to build for Quest.
  2. Open Package Manager and install Input System, XR Plug-in Management, and OpenXR Plugin, using versions compatible with your editor. Keep Packages/manifest.json and packages-lock.json in your repository so your friends get the same dependency versions.
  3. In Project Settings → Player → Active Input Handling, enable the Input System and restart if Unity requests it.
  4. Under Project Settings → XR Plug-in Management, enable OpenXR for the platform you are testing. Desktop and Android have separate settings. Merely installing the package does not enable the provider.
  5. In OpenXR settings, add Oculus Touch Controller Profile for the kit’s supplied controller bindings. Run Project Validation and resolve the required issues for the active platform. For other controllers, add their interaction profile and corresponding bindings to the action asset.

These steps follow Unity’s OpenXR project configuration. The linked package documentation explains the workflow; it is not a claim that version 1.14 is the latest version you should install.

Import and generate#

Copy the kit’s Assets/TrontPhysicsGym folder into your project’s Assets folder, wait for compilation, then select:

Tools → Tront Physics Gym → Create Teaching Scene

The builder creates the playground, player, tracked references, hands, grabbable props, and serialized Input Actions. It also assigns the component references and saves Assets/TrontPhysicsGym/Generated/PhysicsGym.unity (with a unique filename if generated again). Put that scene in your active Build Profile’s scene list. Run Tools → Tront Physics Gym → Run Math Checks and inspect the Console before entering Play Mode. Those checks exercise controller math; they do not test an XR runtime or physical contacts.

The kit owns its camera and tracking transforms. Start with the generated rig; adding another tracked-pose driver or a second locomotion system to the same transforms creates competing writers. XR Interaction Toolkit is not needed for this implementation. If you later integrate it, choose which system owns grabbing, camera poses, and locomotion.

The generated actions use <XRHMD>/centerEyePosition and centerEyeRotation, plus the left/right <OculusTouchController> layouts for poses, tracking validity, grip, and buttons. These are Input System actions, not legacy Input.GetAxis controls. Unity documents the OpenXR input workflow and the Touch control names.

GymRigInput requests a Floor tracking origin. Leave deviceOriginHeightOffset at zero when floor-relative poses are available. If your runtime supplies a Device origin instead, configure the corresponding height offset; adding eye height to an already floor-relative pose raises the whole rig twice. Verify the virtual floor and real controller height before testing locomotion. Unity: tracking origin modes.

First run#

Run the desktop controls first. Use WASD to approach a cube, select the right virtual hand with 2, and move it close with I/K, J/L, and U/O. Press and hold E once the hand is within reach; release and press again if you missed. Keep holding E and press C to switch controllers. Release E to drop the cube. Check that the body falls onto the floor and both hands work before running the OpenXR headset version.

The teaching baseline is a 75 kg player, 1 kg prop, 6 Hz frequency, 1 damping ratio, 1600 N linear force cap, 30 N·m torque cap, and 90 Hz fixed physics step. 2. Keep three different things separate#

Tracked pose: where the real controller says the hand is. It is a reference, and can pass through virtual geometry.

Physical object: the dynamic Rigidbody that collides, has inertia, and can be blocked by a wall. A grab controller applies forces or constraints to bring it toward the reference.

Player body: the Rigidbody that receives the grab reaction and the locomotion motor’s contribution. The tracked hand’s desired world pose moves with this body’s reference frame.

Do not parent a held dynamic object to the tracked hand and also drive it with physics. That gives its pose two owners. Preserve the point and orientation at which the object was grabbed, then drive that attachment toward the hand. The user’s camera follows measured head tracking; it should not be a spring-driven prop. Keep the player, tracking space, and physics-body scales at (1,1,1); use one Unity unit as one metre.

This explains why “use a hand proxy” is incomplete advice. Is the proxy dynamic, and how is it connected to the body? That determines the reaction path. Unity describes the behavior of kinematic rigidbodies.

With custom control, the kit applies the grab force to the object and an opposite force to the player. With a native joint, PhysX supplies the reaction. Do not add the custom reaction on top of the native joint’s reaction.

3. What comes from GorillaLocomotion#

The original source is included under upstream/GorillaLocomotion, pinned to commit bc42e959cf3e69178f9147d89bd3ffeab1c432c4, with its MIT license. Read Another Axiom’s Player.cs alongside the teaching motor.

In that source, Update() sweeps hand positions, computes player displacement from constrained hands, checks head movement, moves the player transform, and maintains a velocity history for launch behavior. It also explicitly zeroes Rigidbody velocity when a hand collides, then can assign a launch velocity. That is deliberate arcade movement code; it is not merely a pair of physical spring hands.

Dropping another force controller onto that player does not guarantee its impulses survive those velocity writes. Decide who owns the velocity at each phase of movement.

Our GymMotor is an adaptation, not an exact port of Gorilla Tag’s feel. Its independent contact architecture selector chooses Off, ForceServo, or CastCorrection. ForceServo uses bounded acceleration toward planted-hand motion. CastCorrection moves the player by an averaged contact correction, constrained by body/head sweeps, and uses a bounded tracked-stroke release rule. Off isolates grab reactions. The active motor can still oppose a grab reaction. The original collision and launch-history code remains a reference, not a claim of parity with this kit.

The 27 November contributor clarification separates velocity-tracked hands, sphere-cast player locomotion, and custom grabbing. We have FireBlast’s description, not his source. Our velocity servo and cast motor are independent teaching examples. Chapter 13 describes the comparison this distinction enables.

Do not attach the original GorillaLocomotion.Player to the generated teaching player at the same time. Experiment with one movement owner at a time, then explicitly design the handoff if you combine them.

5. The four grab controllers#

ConfigurableJoint: let the solver enforce a driven relationship#

A ConfigurableJoint includes drives, limits, frames, collision interactions, and solver behavior. Its spring and damper drive is PD-like, but a whole joint is more than one AddForce formula. PhysX handles coupled constraints within its solver; see the PhysX joint documentation.

The kit puts the joint on the prop and connects it to the player. Its linear drives move the prop’s grab point toward an updated connected anchor, and its Slerp drive handles orientation. The native baseline uses targetPosition = Vector3.zero with a moving connectedAnchor; targetVelocity and targetAngularVelocity are both zero. Thus it does not supply the tracked anchor’s linear/angular motion as native velocity feedforward. Remember this when comparing its moving-target lag with the custom modes.

This A/B compares these implemented configurations. It cannot establish that every ConfigurableJoint is slower than every custom controller. The joint’s per-axis drive limits also differ from a custom controller’s total vector-force clamp.

Relative PD: damp the error in motion#

At the prop’s grab point, define:

C#
Vector3 error = desiredPoint - actualPoint;
Vector3 velocityError = desiredVelocity - actualPointVelocity;
Vector3 acceleration = kp * error + kd * velocityError;

Position error pulls toward the target; velocity error brakes motion that is wrong relative to that target. The actual point velocity must include rotation. Rigidbody.GetPointVelocity(worldPoint) does that; using only linearVelocity treats a spinning object’s handle as stationary relative to its center. Unity: GetPointVelocity.

The kit converts this desired relative acceleration into force using the pair’s reduced mass:

C#
float inverseMassSum = inverseObjectMass + inversePlayerMass;
float effectiveMass = 1f / inverseMassSum;
Vector3 force = effectiveMass * acceleration;

Then it limits the force and applies opposing forces. A kinematic body contributes zero inverse mass. Disabling custom reaction with B excludes the player from this mass calculation and applies force only to the prop. This scalar calculation is a useful translation approximation; it does not solve the full rotational effective mass at two off-center attachment points. It is therefore not an exact replacement for the joint solver.

For the custom modes, frequency and damping ratio set:

C#
float omega = 2f * Mathf.PI * frequencyHz;
float kp = omega * omega;
float kd = 2f * dampingRatio * omega;

Here kp has units of inverse seconds squared and kd inverse seconds. They produce acceleration before mass conversion. Do not paste them into a force-based joint drive without accounting for mass and that drive’s convention. Frequency means natural-frequency parameter in this kit; it is not a guaranteed reciprocal settling time.

Backward PD: account for the discrete step#

The backward mode uses the gain adjustment popularized by David Wu and explained by Digital Opus:

C#
float g = 1f / (1f + kd * dt + kp * dt * dt);
Vector3 acceleration = (kp * g) * error
                     + ((kd + kp * dt) * g) * velocityError;

This softens the effective gains according to the simulation interval. It makes the ideal linear tracking problem more tolerant of high gains and coarse steps. Force caps, delayed input, changing contacts, off-center torque, and a second motor create a different system; they do not inherit a blanket stability guarantee. Digital Opus, Part I.

Digital Opus’s Part II and the Tan, Liu, and Turk SPD paper discuss related next-step methods. The names are not interchangeable. The kit’s BackwardPD mode implements the formula above; the Physics Gym’s other SPD experiments are separately labeled. Increasing a gain cannot make a finite force budget unlimited.

Velocity servo: request a velocity with a finite budget#

The additional VelocityServo mode converts the remaining position gap into a desired closing velocity over the physics step, includes target motion, and corrects the velocity error within a finite force budget. The player receives the paired reaction when enabled. It does not replace the held object’s entire linearVelocity each tick. Rotation has a separately capped angular response.

Frequency and damping are not tuning knobs for this one-step translational servo. Force limits, torque limits, timestep and contact behavior still matter. A velocity request can be aggressive even though it has no compliant spring. This is our comparison mode, not FireBlast’s unreleased grabbing code. Unity and browser implementations use different effective-mass approximations; inspect each source before comparing numerical results.

6. Feedforward, damping, and the One Euro question#

Suppose the hand travels right at a steady speed. A damper written as -kd * objectVelocity pushes left even when the object is perfectly matching the hand. The spring needs a trailing position error to overcome that damping. Raising the damper can therefore make tracking feel soupy.

With kd * (targetVelocity - objectVelocity), an object moving alongside its target has zero velocity error. Expanding the expression gives +kd * targetVelocity - kd * objectVelocity. That target term is what people often mean by velocity feedforward in this discussion. It is already present in relative-velocity PD; adding it again would double it.

Acceleration feedforward is different: it adds an estimate of the target’s acceleration so the controller can begin matching a change in motion before a large tracking error develops. The kit’s optional feedforward is bounded tracking-space hand acceleration, rotated into world space. It excludes acceleration caused by the simulated player body; feeding the reaction-induced body acceleration straight back into the grip can create a feedback loop. Start with it off, then compare reversals and curved hand paths.

A One Euro filter is an adaptive low-pass filter for noisy input. Its cutoff increases with motion speed to trade less lag for less smoothing. It does not change the grab spring’s damping ratio. Nor does it invent a missing target velocity or repair a coordinate-space mistake. Use filtering when measured tracking noise is the problem, after the force law and timing are correct. The kit does not claim to implement One Euro. Original authors’ filter explanation and implementation.

An integral term is also not the first repair. It can accumulate error while a wall prevents the prop reaching its target, then release that stored demand when contact ends. Start with PD, a sensible force cap, and known gravity behavior before introducing integral state and anti-windup.

7. Joint frames: fix these before tuning#

A joint has an object attachment, a connected-body attachment, and axes defining a joint frame. World rotation, local rotation, and joint-space target rotation are different quantities. Unity’s ConfigurableJoint manual defines the anchor, axes, motion modes, and drives.

For the direct connection:

  1. On pickup, store the selected point in the object’s local space. That is the prop-side anchor.
  2. Disable automatic connected-anchor configuration because the controller updates that anchor itself.
  3. Express the desired hand point in the player body’s local space for connectedAnchor.
  4. Preserve the grabbed object’s orientation offset from the tracked hand. Reconstruct the desired object orientation as the hand rotates.
  5. Convert that desired orientation into the captured joint/rest frame. Do not assign the hand’s world quaternion blindly to targetRotation.

Use the kit’s frame helper consistently. If you change axis, secondaryAxis, configuredInWorldSpace, or which body owns the joint, review the conversion as a whole.

A useful verification: rotate the prop 45 degrees before grabbing, then rotate the player’s yaw, and repeat small hand rotations around all three axes. Pickup should not snap the prop to an unrelated orientation. A wrong sign or frame is not fixed by more damping.

For custom torque, use a shortest-arc quaternion error converted to a rotation vector in radians, compare angular velocities in radians per second, and convert angular acceleration through the body’s inertia tensor frame. Inertia is not just mass: a long tool and a compact cube of the same mass resist rotation differently. Unity: inertiaTensor.

The teaching player’s rotation is locked. It does not reproduce the full angular response of a freely tumbling player connected to a prop. Evaluate handheld object rotation here; use a separate unconstrained rig to study full-body torque balance.

The FireBlast preset preserves the reported portion, with our chosen values filling missing implementation details. It is an incomplete reproduction. We also lack his exact collider geometry, joint frames, input timing, solver settings, and proxy-hand arrangement.

connectedMassScale = 8 does not make a 1 kg connected player act like an 8 kg mass to that joint. Unity applies the multiplier to inverse mass and inverse inertia, so it makes that connected body easier for the joint to accelerate. For an isolated translational constraint with equal actual masses and scales 1 and 8, the ideal response split is in the ratio 1:8. Contacts, locked axes, inertia, and the locomotion motor prevent treating that as a measured 89% gameplay result. Unity: connectedMassScale.

Projection is a separate mechanism: it corrects violated constraints geometrically and does not preserve momentum or respect collision geometry. Its distance/angle thresholds primarily concern constrained degrees of freedom; setting 0.02 m does not turn freely driven axes into a universal 2 cm leash. Leave projection off while evaluating a spring drive, then introduce it only for a demonstrated constraint-separation problem. Unity: projectionMode and projectionDistance.

9. Timing, gravity, and release behavior#

Sample controller poses with their tracking context. Perform force calculations and joint updates on the physics schedule. Unity recommends FixedUpdate for Rigidbody force changes because rendering and simulation need not run at the same rate. A 90 Hz physics step is about 11.11 ms; a 120 Hz display does not automatically change it. Unity: Rigidbody.

The kit samples hand targets and estimates bounded velocities in Update; FixedUpdate consumes the latest sample. The camera gets an additional pose refresh before rendering. Acceleration feedforward is a filtered estimate from those hand-velocity samples, not perfect hardware acceleration. Under a render stall, several physics steps may reuse a sample; inspect this timing before blaming the gains.

In the custom modes, desired point velocity combines the player body’s velocity at the desired point with hand motion measured relative to the player’s tracking space. Differentiating raw world-space hand position and then adding player velocity again would double-count the body’s motion.

Reset derivative history at discontinuities: pickup, recenter, teleport, tracking loss/recovery, and a large unexpected pose jump. Otherwise a one-frame displacement becomes an enormous estimated velocity or acceleration. Force limits are a final bound, not a replacement for validating those samples.

Keep gravity enabled while learning how weight transfers. A held object can settle below its target because the spring must produce its weight-supporting force. If you add gravity compensation, label it as a design decision and decide where the corresponding load goes. Disabling prop gravity while held changes the experiment. MIT’s manipulation notes explain PD’s steady-state gravity error.

On release, remove the grab controller and retain the prop’s physically accumulated velocity. Do not add a second full controller throw velocity on top unless you deliberately designed that blend. A wall-blocked prop should not inherit a throw that only the invisible target performed.

The sample immediately restores player–prop collisions on release. Releasing a prop inside the player capsule can therefore cause a depenetration kick. A production refinement is to keep that collision pair ignored until the bodies separate; include overlapping release in your acceptance tests.

Interpolation can make rendered rigidbodies look smoother between physics steps; it does not increase simulation frequency. Keep the physics state and rendered pose distinct when diagnosing lag. Unity: Rigidbody interpolation.

10. Run these experiments in order#

  1. Free-air follow. Hold the small cube, make a slow straight sweep, stop, then reverse sharply. Switch modes while holding. Look for lag, overshoot, and grip offset. Test acceleration feedforward off before turning it on in a custom mode.
  2. Wall pressure. Push the held cube into a wall. The physical cube should stop while the tracked target continues. Observe player reaction and force saturation. Pull away gently; stored controller demand should not launch the cube violently.
  3. Floor support and fixed grips. Press the cube into the floor and move the hand downward. Then grab a fixed climbing rung. Is the reaction sufficient to lift the player? Try custom reaction off to see why one-way object tracking cannot lift a player from a fixed grip. If force is capped below the required load, changing damping cannot fix it.
  4. Rotating tool. Grab away from a prop’s center, rotate through all three axes, and press an end against the wall. This exposes incorrect point velocity, inertia conversion, and anchor definitions.
  5. External impact. While holding a prop still, collide another body with it. Does the system yield, recover, or erase the impact? Compare with the locomotion motor active and inactive when investigating ownership of motion.
  6. Release and reacquire. Release at rest, during a sweep, and while blocked. Regrab a rotated object. Repeat the live mode switch several times. Check the Inspector for orphaned or stacked joints.

Use the same object, grip point, posture, and wall for the A/B. Get Duck or FireBlast to switch modes without announcing the selection, then ask which feels better and why. Record controller mode, mass, gains, cap, fixed step, and headset refresh rate with each conclusion. One nice-looking graph is not enough to choose locomotion feel.

A sensible tuning order#

First fix scale, collision layers, attachment frames, tracking validity, and velocity spaces. Then choose a force/torque budget. Start around damping ratio 1 and increase frequency until recovery is useful. Repeat under contact, not only in free air. If response saturates, decide whether the force budget should change before raising frequency again.

Increase solver iterations locally on the player and held prop only when you can reproduce a joint/contact convergence problem. More iterations cost CPU and do not correct a bad target frame. Profile on the headset; desktop success is not a Quest performance result. Unity: solverIterations.

The browser’s point joint leaves rotation free, with no angular motor. Acceptance checklist before sharing a build#

  • Fresh Unity import compiles without errors; generated scene and action references are present.
  • Desktop grab, release, restart, and all four live grab selections and all three contact architectures work.
  • Headset floor height, scale, left/right poses, grip input, and turning are correct.
  • Tracking interruption and recentering do not generate a large impulse.
  • The same held object survives repeated CJ → relative PD → backward PD → velocity servo switches.
  • Wall and floor contacts transfer load through the intended body/proxy path.
  • Rotated pickup and all-axis tool rotations preserve the captured grip.
  • Releases preserve sensible physical momentum without a duplicate throw boost.
  • No growing number of joints, orphaned holds, or persistent collision-ignore pairs.
  • Native headset frame timing has been measured at the chosen refresh rate.
  • Another person has performed the in-headset A/B and described the difference.

Each prop has one owning hand; a two-handed rifle grip needs additional logic. This kit stops at local interaction. Multiplayer ownership, authoritative physics, reconciliation, avatar presentation, and networked throws require a separate design. First establish a grip that feels good and behaves predictably on one headset.

13. Architecture and replay#

The latest contributor clarification makes three responsibilities explicit: velocity-tracked hands, sphere-cast locomotion, and a separate grab controller. FireBlast has not supplied his implementation here. The examples in this repository demonstrate those choices independently; they do not reproduce his unpublished rig.

Use Unity N / Touch B to cycle the contact architecture, independently of C / Touch A for grabbing. The browser has a Player contact selector and a triggerable Contact mode button inside VR. Switching either selection keeps the current prop held.

Cast correction averages planted-hand displacement and moves the body subject to collision checks. A release rule derives launch from deliberate tracked strokes. Force servo uses a finite response to contact demand. Off removes the empty-hand locomotion contribution so a grabbing reaction can be observed on its own. Engine body collisions and gravity still exist.

The browser hands are massless query/attachment points. They are not a second set of dynamic hand rigidbodies. Its conservative expanded-box sweeps operate against static boxes. A browser floor test therefore does not validate a Unity rig’s capsule contacts, moving support behavior or full articulated hand inertia.

Comet’s mid-air question#

Native PhysX drives participate in the solver and can handle coupled constraints more robustly than a force computed once before the solve. Their drive law is itself PD-like. Both approaches actuate the simulation; “real versus fake forces” is not the useful distinction. Mass scaling and projection can also deliberately change physical behavior. See the PhysX joint documentation.

An internally actuated dynamic hand/body pair can conserve total momentum while the player body moves opposite the hand. That reaction can be physically consistent and still undesirable in a VR camera rig. A missing reaction, a velocity overwrite, or counting body motion twice is a different problem. Measure body motion, reaction, and input reference frames separately.

In the browser Airborne arm sweep uses zero gravity, no grip and free-space hand targets to isolate whether ordinary empty-hand tracking moves the player. It does not simulate a complete normal-gravity jump or inertial hand bodies. For held-prop recoil, use manual input and the external-impulse experiments too.

Choose 72, 90 or 120 Hz separately from rendering. Turn Repeat experiment off to keep recording after the motion sequence ends; this does not pause the simulation. Reset before a fresh controlled comparison. Export current trial for settings and aggregate measurements.

Compare all controllers uses a background module Worker. It records one baseline body-local head/hand sequence, including hand orientation and grip state, then replays those exact samples in a fresh world for every grab mode. The source workout adjusts its first reach to the settling cube; recording once prevents each controller from receiving a differently adapted input.

Every result contains the same input fingerprint, the initial-state snapshot, selected environment settings and the complete recording. This fingerprint is an audit aid, not a cryptographic signature. A trace created for one scenario, physics rate or engine implementation must not be silently reinterpreted as another.

Read the scoreboard as several observations:

  • Held / grip requested: how often a requested grip resulted in a held object. A controller that never acquired anything does not earn a perfect tracking score.
  • RMS and peak gap: measured only while an object is held. No held samples produce null in the export and “No held samples” in the UI.
  • Peak displacement: distance from the player’s starting origin. In locomotion tests that can be intentional movement, not an error.
  • Force cap: fraction of held samples at the drive limit. The native point constraint’s axis limits and custom vector limits remain different.
  • Final speed: motion left at the end of the recording. Inspect the action trace and contacts before treating more speed as better.

A successful replay is not a universal ranking. The freely rotating point joint differs from orientation-driven modes. A different policy can also learn to exploit a controller that performs poorly under this particular recording.

Public environment boundary for learning code#

vr/experiments.js exports GrabEnvironment, ACTION_SCHEMA, and OBSERVATION_SCHEMA. It contains no neural network, optimizer or pretrained policy. It exposes the physics experiment to an independently written trainer through a small stable interface:

The eight actions are left x/y/z/grip, right x/y/z/grip, each in [-1,1]. Position components are shoulder-relative offsets in units of maximum arm length; vectors outside the unit sphere are projected onto it. Positive grip closes the hand. This intentionally narrow adapter fixes the head and requests identity hand rotations. Recorded traces support orientations, but this eight-action policy interface does not yet output them.

The thirty observations include player displacement and velocity, each hand’s local target and velocity, held/contact flags and held gap, plus the small cube’s relative position and velocity. observe() returns both raw values and values divided by the exported scale and clipped to [-5,5]. Read OBSERVATION_SCHEMA for the authoritative order and units; never guess them from a neural-network input count.

The episode truncates at its configured time limit. A nonfinite body state or player outside the explicit evaluation bounds terminates it. A missing cube or failed grip alone is not secretly rewarded or classified as task success.

reward: null is deliberate. Choose an objective before training: acquire and hold a cube, reach a surface, or move the player toward a waypoint. Include limits on force demand and failed states, and ensure the agent cannot increase reward by exploiting penetration recovery or abandoning the task. Evaluate on scenarios and input sequences excluded from tuning.

A saved brain from another experiment requires matching observations, normalization, actions, decision cadence, physics and objective. Shape-compatible arrays alone do not make it transferable. The public adapter is a place to connect an appropriate trainer; this release does not claim a learned policy has been trained or validated in the gym.

Moving supports and next boundaries#

For a moving support, store the contact relative to the support and reconstruct it in world space as that support moves. Point velocity includes both translation and rotation. Unity’s GetPointVelocity accounts for angular velocity.

Release velocity must include carrier motion once. A world-space velocity estimate may already contain it; adding a second full carrier velocity invents an extra boost. The Unity teaching motor has support-relative contact data, but translating/rotating-platform behavior still needs runtime acceptance. A collider moved directly by its transform also needs a deliberate velocity estimate if the physics body does not report the intended motion. The browser room’s supports remain static.

Ziplines, portals, moving-platform scenes, network authority, fully dynamic hand proxies and physical-headset performance are not completed features of this release. They need their own geometry, velocity ownership and acceptance tests. The current lab supplies controlled local experiments and exportable evidence for that work.

14. Gorilla locomotion, then physics#

This chapter is the path this project is for: start from the popular default Gorilla Tag player, understand why it moves, then make it physics-based with a ConfigurableJoint and a few supporting tricks. The Gorilla course is the Three.js half. It runs the default locomotion; the Unity half below is where it becomes physical.

What has been verified. The JavaScript port and the course tests run in Node and a browser. The Unity code in this chapter is design guidance: it was not compiled in Unity or tried in a headset while writing. Treat the snippets as a starting point and check joint frames with chapter 7.

The default player does not use forces#

In Player.cs there is a Rigidbody, but locomotion is not force-based. Each frame the player sweeps a small sphere for each hand toward the tracked hand, remembers where it hit, and moves the whole player by the opposite of the stuck hand’s motion. Gravity and the launch come from the Rigidbody only because the script writes its velocity. That is why it feels crisp, and also why it is hard to mix with joints, held objects or other forces.

The course page ports that loop to plain JavaScript (gtag/gorilla.js) so you can read it next to the C#:

The port keeps the same order of operations. Three things you will notice on the course#

  1. Pressing hard launches you. Plant a hand on the floor too fast and its correction becomes upward velocity. Ease it down until it sticks, then pull. The scripted player does this and the tests check it.
  2. A stuck hand sticks where it touched. To climb a wall you cannot slide a hand up it. Lift the hand off, move it up in the air, then press in. Pressing deeper each frame pushes you away from the wall; the scripted player has no reliable wall routine yet (this is the likely reason), so that stage is by hand.
  3. Two hands average. Two stuck hands pulling the same way move you as far as one, not twice as far. There is a test for it.

From default to physical, in steps#

Keep the original working as a reference and change one thing at a time. Chapter 3 explains why only one component may own the player’s velocity.

Step 1. Give the hand a body. Add a Rigidbody (mass 1 to 2, continuous collision) and a sphere collider on the world layer. The tracked hand stays a transform that only describes where the player’s hand is.

Step 2. Tether the hand body to the player with a ConfigurableJoint. The joint’s drive is the force that pulls the physical hand toward the tracked hand.

C#
var tether = handBody.gameObject.AddComponent<ConfigurableJoint>();
tether.connectedBody = playerBody;
tether.autoConfigureConnectedAnchor = false;
tether.connectedAnchor = Vector3.zero;
tether.xMotion = tether.yMotion = tether.zMotion = ConfigurableJointMotion.Free;
var drive = new JointDrive { positionSpring = spring, positionDamper = damper, maximumForce = maxForce };
tether.xDrive = tether.yDrive = tether.zDrive = drive;
// Each FixedUpdate, set tether.targetPosition from the tracked hand in the player's frame.
// The sign and frame of targetPosition are easy to get backwards: use the checks in chapter 7.

Because a joint applies equal and opposite force, a hand that is blocked by the world pulls the player the other way. That is the physical version of “the stuck hand moves the player”. It also means the hand has a finite strength (maximumForce) instead of an infinite one.

Step 3. Make a hand stick. The default player sticks by geometry. In physics, pin the hand body to the world point it touched with a second joint that has no connected body, and drop the pin when the tracked hand is farther than unStickDistance from it.

C#
var pin = handBody.gameObject.AddComponent<ConfigurableJoint>(); // connectedBody == null: world
pin.autoConfigureConnectedAnchor = false;
pin.anchor = handBody.transform.InverseTransformPoint(contactPoint);
pin.connectedAnchor = contactPoint;                              // world space
pin.xMotion = pin.yMotion = pin.zMotion = ConfigurableJointMotion.Locked;

Pulling the tracked hand back now stretches the tether, and the tether’s reaction moves the player. The averaging of two hands falls out of the solver instead of being coded.

Step 4. Replace the velocity write. Delete the launch assignment. Momentum now comes from the reaction forces. If you want the arcade jump back, scale the tether’s maximum force or the player’s inverse mass seen by the joint (connectedMassScale) as a tuning knob, not a velocity overwrite. The kit already has this trade-off for grabbing in chapters 5 to 7.

Step 5. Held objects load the player. Gripped objects use one of the grab controllers from chapter 5, with the player as the other body. A heavy object now costs you launch and speed because it is part of the same force balance. The course’s carry stage shows the simplest approximation of that: a gripped cube shares your launch momentum (bodyMass / (bodyMass + heldMass)). It is a teaching shortcut, not a joint.

Step 6. Check the timing. Run hand and body logic in FixedUpdate, interpolate the visuals, and keep solver iterations high enough that a pinned hand does not stretch. Chapter 9 covers gravity and release behaviour.

What is in the kit and what is not#

The kit’s GymMotor has ForceServo, CastCorrection and Off for empty-hand locomotion, and GymHand has a real ConfigurableJoint for grabbing. The tether-plus-pin hand in Steps 1 to 3 is not in the kit yet. It is the next thing to build and test in Unity, and the course gives you the behaviour to compare against.

The scripted player and the interface#

The course page runs a scripted player through the same 8-number action and 27-number observation vector (gtag/env.js) that a human adapter or a learned policy would use: left and right hand targets as head-relative offsets, plus a grip each. It labels what it is doing (“walk: right hand pull”, “push-up: press”). Because hands are commanded as targets, the same player can later drive the Unity tether in Step 2 unchanged, and you can compare the default and physical versions on the same stages.

It completes slap, push-up steps, carry and gap from the standard spawn. It is brittle if the spawn moves, and it does not climb the wall. The tests in vr/tests/gtag.mjs list what passes. No neural network is included: the interface is the boundary a trained policy would plug into.
